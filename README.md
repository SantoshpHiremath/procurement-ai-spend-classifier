# Procurement Spend Classification & Data-Quality AI Tool

A real, tested Python tool that takes messy, inconsistent purchase-order
line-item data (as real ERP/procurement exports actually look) and applies
AI to two concrete procurement problems: recovering a usable spend category
from free-text item descriptions when the category label is missing or
inconsistent, and flagging likely duplicate invoice lines and price
outliers for a category manager to review — built to close a specific gap
for Knorr-Bremse's "Working Student AI & Data in Procurement" posting: an
AI use case framed specifically in procurement terms, which nothing in my
prior project portfolio had done.

## What this is (read before citing anywhere)

**All data is synthetic**, generated by `src/generate_data.py` — not real
Knorr-Bremse, supplier, or spend data. I have not worked with a real
procurement or spend-management system. What's built here demonstrates the
underlying skill — structuring messy business data for an AI application,
building a working classifier, and verifying it against known ground
truth — on a system I could construct and test myself, not prior
procurement-domain experience.

## The use case

Procurement teams commonly need to categorize spend (by material type,
commodity group, etc.) for reporting and sourcing strategy, but the
category field in real ERP exports is often missing, abbreviated, or
inconsistently entered — while the free-text item description is reliably
present. This mirrors a genuine, common procurement AI use case: spend
classification from unstructured text.

- **`src/generate_data.py`** — generates 4,214 synthetic PO line items
  across 6 spend categories (Raw Materials - Steel, Raw Materials -
  Rubber, Electronic Components, MRO - Maintenance Supplies, Packaging &
  Logistics, IT & Office Equipment) and 15 supplier names, with realistic
  messiness: ~44% of rows carry a missing or non-canonical category label,
  descriptions include typos, truncation, inconsistent casing, and
  irrelevant boilerplate, and some item types (e.g. "sealing gasket",
  "connector", "protective foam sheet") deliberately share vocabulary
  across categories so the classification task isn't trivially easy.
- **`src/classifier.py`** — a TF-IDF + logistic regression classifier
  trained on description text only (never on the messy `category_raw`
  field, which would leak the very thing it's meant to fix). Directly
  implements "structuring and preparing data for AI applications" and
  "translating a business need into an AI use case."
- **`src/anomaly_checks.py`** — duplicate invoice-line detection (same
  supplier, description, price, and quantity) and price-outlier detection
  within a spend category, using the same robust median/MAD z-score method
  as an earlier anomaly-detection project — a data-quality use case aimed
  at overpayment and pricing-error risk that a category manager would
  otherwise have to find manually.
- **`src/pipeline.py`** — runs the full flow end-to-end and prints a
  management-style summary.

## Verified against known ground truth (not just "it runs")

- **Classification accuracy**: 99.6% on held-out test data — high because
  the task is genuinely learnable from description text, but deliberately
  not 100%, because a perfect score here would mean the synthetic data
  was too easy (disjoint per-category vocabulary with no realistic overlap
  or noise), not a validated model. A test asserts accuracy stays in a
  realistic 90–99.9% band rather than allowing either extreme to pass
  silently.
- **Recovering messy labels**: of the 1,855 rows with a missing/
  non-canonical category in the raw export, 1,851 (99.8%) were correctly
  reclassified from the description alone.
- **Duplicate detection**: all 14 deliberately injected duplicate invoice
  pairs are caught, confirmed with an exact-match test.
- **Price outliers**: all 3 deliberately injected price outliers (5.5–6x
  the category's normal price) are caught, confirmed with an exact-match
  test.

## Two honest findings from development

Documented here rather than silently fixed or hidden, because catching
and explaining them is part of the evidence this project provides.

1. **Baseline contamination in small groups (a real bug I found and
   fixed).** The first version injected 3 price outliers into a
   description group with only 10 rows. Because 30% of that small group
   was outliers, the outliers themselves dragged the group's own
   median/MAD statistics enough that 2 of 3 fell under the detection
   threshold — the same class of issue as a rolling baseline getting
   contaminated by the anomaly it's supposed to detect. Fixed by requiring
   a larger minimum group size (≥25 rows) before injecting outliers into
   it, which is also more realistic: a category manager wouldn't act on
   an outlier signal from a group of 10 purchases. A regression test
   guards against this threshold silently regressing.
2. **Duplicate detection also catches genuine coincidental matches, not
   just injected ones — and that's correct behavior, not a bug.** With a
   small fixed set of quantities and near-fixed prices for some low-
   variance items (e.g. EUR pallets), two independently generated rows
   can legitimately match on every key field by chance. The detector
   flags these too. This is disclosed rather than filtered out, because a
   real category manager reviewing flagged duplicates would face exactly
   this ambiguity — same supplier, same description, same price, same
   quantity — and would need to check whether it's the same invoice
   entered twice or a genuine coincidence, which this tool surfaces
   rather than silently resolves either way.

There is also an expected, disclosed false-positive rate on price
outliers beyond the 3 injected cases: because unit prices are drawn from
wide uniform ranges in the synthetic generator, natural variance alone
occasionally exceeds the z-score threshold. This is normal for the
method and is not tuned away by loosening the threshold, which would risk
hiding real outliers instead.

## Running it

```bash
pip install -r requirements.txt
python3 src/pipeline.py     # generates data, trains classifier, runs checks
pytest tests/ -v             # 10 tests, all verifying real ground truth
```

## What this doesn't demonstrate

This project doesn't use a real spend taxonomy (e.g. UNSPSC), doesn't
integrate with any real ERP or procurement system, and the supplier/
category list is illustrative, not based on any real sourcing strategy.
It demonstrates the underlying pattern — turning messy business data into
an AI-assisted classification and review tool, with the result honestly
verified against ground truth — which is the skill the posting asks for,
not claimed procurement-domain expertise.
